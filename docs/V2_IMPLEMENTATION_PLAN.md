# pilot V2 Implementation Plan

## Current architecture

- Vinext/React 19 application rendered through a Cloudflare Worker and deployed with OpenAI Sites.
- The main V1 experience is a single client component (`app/SydneyApp.tsx`) with local demo persistence in `localStorage`.
- Today, Week, Closet, and History are tab states rather than URL-backed routes. Existing weather, calendar, garment-analysis, and recommendation endpoints are server routes under `app/api`.
- Garment and recommendation demo data live in `lib/demo-data.ts`; deterministic eligibility rules live in `lib/recommendation.ts`.
- Supabase migration `0001_initial.sql` defines profiles, calendar connections, garments, outfits, contexts, recommendations, wear history, feedback, private garment storage, and RLS.
- The production build is generated by Vinext/Vite and deployed as a Cloudflare-backed private Site using `.openai/hosting.json`.

## Reusable V1 product pieces

- Warm ivory, charcoal, sage, quiet-border editorial design tokens.
- Serif display typography and compact sans-serif UI typography.
- Chicago weather and Office to Dinner demo context.
- Three recommendation types and deterministic garment availability filtering.
- Week planning, closet filters, laundry state, wear history, feedback, Calendar fallback, and add-item flow.
- Existing server/client separation for secret-backed API calls and existing Supabase ownership policies.

## Existing database tables

`profiles`, `calendar_connections`, `garments`, `outfits`, `outfit_items`, `daily_contexts`, `recommendations`, `recommendation_items`, `wear_history`, and `feedback`.

V2 adds `person_profiles`, `person_reference_photos`, `garment_assets`, `outfit_layouts`, `try_on_sessions`, `try_on_jobs`, `try_on_results`, `scene_presets`, and `generation_feedback`, plus private storage buckets for reference photos and generated previews.

## Existing image handling and visible V1 issues

- V1 uses remote retailer and editorial image URLs, so imagery can fail, drift, or be blocked.
- Recommendation cards show full photography rather than the individual pieces in the recommendation.
- Closet images have inconsistent crops, backgrounds, scale, and model photography.
- Week and History repeat flat thumbnails and do not expose a try-on path.
- The four-item bottom navigation has no dressing-room entry.
- The Today hero is too tall on common laptop viewports and the fixed navigation can crowd final content.
- Upload previews are browser object URLs only; there is no V2 asset-processing state, private reference-photo model, or deletion workflow.

## V2 implementation

1. Replace remote hotlinks with a stable local starter closet and transparent, consistently lit garment assets.
2. Add shared `OutfitComposition` and garment tile components with deterministic category placement, overlap, scale, depth, and reduced-motion behavior.
3. Upgrade Today, Week, Closet, outfit details, and History while preserving all V1 interactions.
4. Add URL-aware navigation with a central Try On entry and a presentation-ready dressing-room flow: context, outfit, photo, review, Mirror result, and optional scene result.
5. Add model-photo setup with consent, structured technical-quality guidance, default selection, deactivation, and deletion controls.
6. Implement background-removal and try-on provider interfaces with deterministic mock providers and optional server-only OpenAI providers.
7. Persist resumable demo sessions/results locally; define production persistence and RLS in Supabase migrations.
8. Add calm loading/failure states, request hashing, retry boundaries, and private-context normalization.

## Image and personal-photo strategy

- Starter garments are local generated demo assets, not scraped or hotlinked retailer images.
- The presentation deployment is private. User-supplied model photos are EXIF-stripped and downsampled before being included as explicitly seeded private-presentation references.
- Production personal photos are designed for a private Supabase bucket and signed-URL access; the browser never receives service-role credentials.
- The default supplied photo is selected only by technical utility (one person, sufficient body visibility, usable light), without appearance or sensitive-trait analysis.
- Demo assets and personal-photo references are labeled separately in the product and documentation.

## Migration strategy

- Keep `0001_initial.sql` unchanged as the V1 baseline.
- Add an additive `0002_v2_dressing_room.sql` migration containing new tables, indexes, triggers, private buckets, and ownership RLS.
- Use intentional cascades from a user/profile/session to derived jobs, results, and feedback.
- Keep garments and wear history backward-compatible; a virtual result does not become wear history until the user explicitly selects Wear this.

## Rollout phases

1. Audit/foundation and documentation.
2. Stable garment assets and dimensional composition system.
3. V2 visual upgrade across existing screens.
4. Dressing Room and deterministic mock providers.
5. Private model-photo controls and persistence model.
6. Optional OpenAI image provider and server-owned prompts.
7. Lint, typecheck/build, unit/integration smoke tests, accessibility review, and private deployment.

## API and environment requirements

- Demo defaults: `NEXT_PUBLIC_DEMO_MODE=true`, `TRY_ON_PROVIDER=mock`, `BACKGROUND_REMOVAL_PROVIDER=mock`.
- Optional live image generation: `OPENAI_API_KEY`, `OPENAI_IMAGE_MODEL`, `OPENAI_IMAGE_QUALITY`.
- Optional background removal: `BACKGROUND_REMOVAL_PROVIDER=openai|rembg_http`, `REMBG_SERVICE_URL`.
- Existing optional integrations remain: Google Calendar, Supabase, OpenAI recommendations, and server-side token encryption.

## Privacy and security

- Personal tables are user-owned, indexed, RLS-protected, and queried using the authenticated server user rather than a client-provided user ID.
- Reference photos and generated results use private buckets and signed URLs.
- Strip EXIF before storage; never log raw images, signed photo URLs, provider prompts, exact private addresses, or raw Calendar descriptions.
- Normalize private locations before provider use and redact provider errors returned to clients.
- Support deleting one photo/result and deleting all reference photos/derived try-ons.
- Demo mode never silently pretends to be a live provider; seeded outcomes are visibly identified as presentation previews.

## Testing plan

- Unit coverage: outfit layer calculation, garment conflict resolution, request hashing, prompt construction, private-location/calendar normalization, job transitions, and feedback updates.
- Integration coverage: session creation, mock Mirror/scene creation, result saving, marking worn, laundry impact, personal-data deletion, and ownership policy presence.
- Rendered application smoke coverage for Today, Week, Try On, Closet, History, and no-service fallbacks.
- Build/lint checks plus responsive CSS review at 390x844, 430x932, 768x1024, 1366x768, and 1440x900.

## Known presentation boundary

The default deployment uses deterministic seeded Mirror and scene previews so it is reliable without external credentials. The OpenAI provider path is implemented behind configuration, but live identity-preserving generation requires a valid server key and production private storage.
